# Спецификация: приходы и импорт записей из Excel

По замыслам `intent/2026-09-28-…` (п. 7, приходы), `intent/2026-09-30-…`
(задача 5, импорт), `intent/2026-10-01-…` («в экспорт попадают не все
данные»). Решения Mike 02.10.2026: приход — отдельный файл; общие
справочники — отдельным общим файлом; дело — на год; импорт в программе;
проверка — на нашей стороне; одна сборка, без мелочи (она — следующим
спринтом).

Ответы Романа 02.10 (его словами):
- файлы нужны, чтобы «вести параллельную работу — индексировать сразу
  несколько приходов одновременно, переключаясь между ними, либо начинать
  работу над новым приходом с чистого листа … не смешивая данные в одну кучу»;
- сценарий: «взять свой старый Excel-файл, загрузить его в GenMetric, чтобы
  старая база стала отправной точкой. Далее я продолжаю вносить новые записи
  уже через интерфейс … итоговая выгрузка должна включать весь приход
  целиком: объединить старые данные, загруженные из Excel, с новыми»;
- дело: «каждый год, как правило, представляет собой отдельное архивное
  дело. Текущий подход к заполнению реквизитов вполне удобен … **Менять эту
  логику не нужно**».

## 1. Приход — файл

1.1. Каждый приход — самостоятельный файл SQLite той же схемы, что нынешняя
база: справочники поставки, записи, память персон, причт. Программа держит
открытым один приход. Запросы, выгрузка и обновление (`migrate.sql`,
отпечаток поставки) не меняются: обновление проходит у каждого файла при
его открытии — тем же `open_database`.

1.2. Нынешняя база `genmetric.sqlite` остаётся на месте и становится первым
приходом (название — село из её дела). Новые приходы — в подпапке `приходы/`
папки данных, файл `<номер>-<название>.sqlite`.

1.3. Перечень приходов и всё общее — в файле `genmetric-общее.sqlite` рядом:
таблица приходов (название, файл, когда открывали), общие справочники
(п. 2), настройки окна (масштаб, поверх окон, свёрнут ли причт, карточка
«Для Familio»). Какой приход открыт — там же; при запуске открывается
последний.

1.4. Экран «Дело», верх: «Приход: Борисоглебское» и кнопка «Сменить…». Окно
«Приходы»: список (название, число записей, когда открывали), «Открыть»,
«Новый приход…» (название → пустой файл из поставки, без причта и персон),
«Импортировать из Excel…» (п. 4). Смена прихода: недосохранённую запись
программа не теряет молча — предупреждает, как при «Открыть» записи. После
смены окно перечитывает всё заново; название прихода — в заголовке окна.

1.5. Удаления прихода в этой сборке нет (файл можно убрать руками; в
перечне он помечается «файл не найден»).

Критерии: `db/test_parish.py` (перечень, создание, пустой приход без персон и
причта, настройки окна общие); тест крейта на открытие/создание; e2e на
Windows — создать приход, набрать запись, вернуться в первый, записи не
смешались.

## 2. Общие справочники

2.1. Общее для всех приходов (Роман 28.09: «справочники НП и званий — общие»):
населённые пункты с карточками и памятью переименований; все пополняемые
перечни (`lookup`, origin = user: звания мужские, женские, причта, причины
смерти, родство, архивы, церкви, уезды, губернии, типы НП); соответствия
имён из окна сверки (`name_alias`). **Не общее:** персоны, жёны, причт,
частоты подсказок, записи.

2.2. Как: при открытии прихода — сверка в обе стороны (чего нет в общем
файле — туда; чего нет в приходе — в него). При каждом сохранении карточки
НП, пополнении перечня и решении в окне сверки — запись сразу и в общий файл.

2.3. Спор о подробностях одного пункта (по `name_norm`): заполненное
побеждает пустое; при двух разных заполненных — более позднее
(`place.updated_at`, новая колонка без NOT NULL и DEFAULT). Названия не
затираются: переименование идёт своей памятью (`place_renamed`).

2.4. Сбой сверки не мешает открыть приход: полоса с сообщением (`report`),
работа продолжается со справочниками прихода.

Критерии: `db/test_parish.py` — пункт, заведённый в приходе А, после
открытия Б есть в Б с подробностями; звание — так же; персона из А в Б не
подсказывается; правка карточки в Б доезжает до А; пустое не затирает
заполненное.

## 3. Дело — на год книги

3.1. Проблема: реквизиты (архив, фонд, опись, дело) сейчас одни на всю базу,
а у каждого года книги своё дело — в Excel Романа 1889 год «Ф.56 Оп.31
Д.11», 1890 — «Д.12». Выгрузка в Familio ставила бы всем годам одно дело.

3.2. Решение без смены привычки (Роман: «менять эту логику не нужно»).
Экран «Дело» остаётся одной формой. Внутри у каждого года книги своя строка
`mk_case`; запись привязывается к делу своего года книги (год формы) —
привязку ставит программа при сохранении. Первый раз встретив новый год,
программа заводит ему дело копией последнего и говорит жёлтой полосой:
«Новый год книги 1898 — проверьте фонд, опись и дело на экране „Дело“».
Экран «Дело» показывает и правит дело текущего года (год последней записи);
в заголовке — «Дело за 1897 год» со списком годов, чтобы поправить реквизиты
прошлого года (после импорта у 1886–1888 они пусты).

3.3. Церковь, село, уезд, губерния, индексатор — свойства прихода: правка
на экране «Дело» расходится на все годы. Архив — на все годы, где он пуст.

3.4. Запросы, смотревшие «в своё дело», смотрят в приход (файл): список
«Набрано» — записи текущего года книги («Набрано рождений за 1897: 39»),
иначе после импорта в списке была бы тысяча строк; «продолжить с места» — по
последней записи раздела; дети для подсказки умершего и отец из записи о
рождении — по всему приходу (умерший в январе родился в прошлом году);
причт — по последней записи прихода.

3.5. У уже установленной программы: единственное дело получает год записей,
которые к нему привязаны; если годов несколько — записи других годов
получают свои дела копией (`migrate.sql`, проверка в `test_upgrade.py`).

Критерии: `test_entry.py` — запись нового года заводит дело, реквизиты
прежнего года не меняются; `test_export.py` — у записей разных лет в Familio
свои фонд/опись/дело; стенд — полоса о новом годе, «Дело за … год».

## 4. Импорт из Excel-индексатора

4.1. «Импортировать из Excel…» в окне «Приходы»: выбор файла `.xlsm` /
`.xlsx`, файл уходит в программу частями (он 7 МБ; байты — обычными
аргументами, грабли 13.09). Программа проверяет, что это индексатор (листы
«1», «2», «3» с ожидаемой шапкой), создаёт **новый приход** и переносит в
него записи. В открытый приход не добавляется ничего.

4.2. Что переносится (колонки — разбор эталона, спека #39):
- дела по годам: архив, «Ф. Оп. Д.» → фонд, опись, дело; церковь, село, уезд,
  губерния — из колонки «МК»;
- рождения: страница, счёт М/Ж, даты рождения и крещения, ребёнок (пол — по
  колонке счёта), отец, мать (девичья — из скобок), восприемники 1–2, причт 1–3;
- браки: дата, жених и невеста (каким браком, лет), родственники жениха и
  невесты с родством, поручители 1–4 со стороной, причт;
- смерти: даты смерти и погребения, умерший (звание, причина, возраст как в
  книге и разобранный), родственник (родство — из листа «МК»: «умершего
  отец»; нет — «отец»), причт;
- у каждой персоны: НП, звание, вероисповедание, примечание.

4.3. Каждая запись проходит **тем же путём, что и набранная руками**: тот же
разбор ИОФ (словарное имя, современное отчество, соответствия из окна сверки),
то же сохранение — пункты заводятся, звания попадают в перечни, память
персон, жён и причта и частоты подсказок растут. Поэтому после импорта
подсказки «прогреты», а выгрузка не отличает импортированное от набранного.
Для этого сохранение записи, разбор ИОФ и разбор возраста переезжают в крейт
`genmetric-core` (возраст — перенос `age.ts` на Rust, сверка по тем же
примерам, что `scripts/test_age.mjs`).

4.4. Имя, которого нет в словаре, переносится как в Excel, без окна сверки.
Итог импорта — на экране: сколько рождений, браков, смертей, персон, пунктов;
сколько имён не сверено (и первые из них); сколько строк пропущено и почему.
Пропущенная строка — не молча.

4.5. Импорт — одной транзакцией в новом файле: ошибка — файл прихода не
создаётся, перечень не меняется. Повторный импорт того же файла (по имени и
размеру, записанным в приходе): программа спрашивает — заменить тот приход
или создать ещё один.

4.6. Сценарий Романа «импорт → продолжаю набирать → выгружаю весь приход»:
после импорта открыт новый приход, формы продолжают с последней записи
(страница, счёт, год, причт), выгрузки — весь приход.

Критерии: синтетический индексатор-фикстура (собирается скриптом, в
репозитории) → импорт → проверки по колонкам в тесте крейта (в конвейере);
e2e на Windows — импорт фикстуры через окно, записи в формах, выгрузка.

## 5. Проверка на данных Романа («золотая», только у Mike)

Тест крейта `import_golden` (помечен ignored, путь к его `.xlsm` — переменной
окружения): импорт → выгрузка в Familio → сверка с листами `f - 1`, `f - 2`,
`f - 3` его файла по каждой колонке. Колонки, где мы намеренно не как
индексатор (причт по званию, поручители по стороне, звание отцов, Н.П. без

остальных — доля совпадения и список расхождений. Порог: ФИО, отчества,
даты, звания, места, страница, счёт — совпадение не ниже 99 %, каждое
расхождение объяснено (ошибка индексатора из списка спеки #39 или наша).
Результат — в отчёте Mike перед выкладкой. Число записей: 1085 / 180 / 824.

## 6. Порядок работы

1. Крейт: сохранение записи, разбор ИОФ и возраста — в `genmetric-core`
   (поведение не меняется; тесты те же).
2. Дело на год (схема, `migrate.sql`, запросы, экран «Дело»).
3. Приходы: общий файл, перечень, открытие/создание, сверка справочников, окно.
4. Импорт: чтение xlsx, перенос, отчёт, окно.
5. Золотая проверка; стенд; e2e; агенты; громкое напоминание.

## Чего сознательно не делаем

Удаление и переименование прихода; передача прихода другому человеку
отдельной кнопкой (файл можно скопировать); слияние двух приходов; импорт
листа «МК» как источника (берём «1–3», из «МК» — только родство у смертей);
вся мелочь из П2–П4 (карточка НП, двойники, Inter, «в столбик», macOS arm64)
— следующим спринтом.

## Как сделано — отличия от написанного выше (02.10.2026, после агентов)

- П. 1.4: с несохранённой записью (и с несохранённой правкой экрана «Дело»)
  приход не меняется вовсе — программа отказывает и говорит, какая форма не
  сохранена; так же устроено «Открыть» записи.
- П. 2.3: время правки карточки пункта — с миллисекундами; название, которое
  человек вернул после переименования, снова становится общим пунктом.
- П. 3.2: полоса о новом годе — заголовок «Новый год книги N» и пояснение
  строкой ниже. Экран «Дело» не затирает год дела пустым.
- П. 3.4: дети для подсказки умершего и отец из записи о рождении — не по
  всему приходу, а за 7 лет до года формы смертей (после импорта тринадцати
  лет частое имя иначе не попадало в список).
- П. 4.1: перед импортом программа показывает, что в файле, и спрашивает
  название прихода (по умолчанию «<село> (из Excel)»).
- П. 4.4: в отчёт идут ещё и оговорки — строки, перенесённые не дословно
  (нет года, странная дата, заглушка вместо имени умершего, родство против
  пола имени, звание без имени), и отчества вне словаря.
- П. 1.3: если общий файл пропал, приходы из папки `приходы/` возвращаются в
  перечень сами.
- П. 5: сверка «золотая» — в две ступени: «туда-обратно» с листами «1», «2»,
  «3» (порог 99 % по каждой колонке, получено 99,9–100 %) и сравнение с
  листами `f - 1…3`, где расхождения — намеренные отличия спеки #39, В5.
